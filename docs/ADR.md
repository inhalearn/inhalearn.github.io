# Architecture Decision Records

## 철학
**MVP 속도 최우선. 10분 실습에 최적화. 모바일 우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택.**

---

### ADR-001: React + Vite (Next.js 대신)
**결정**: React 18 + Vite로 SPA 구현
**이유**:
- GitHub Pages는 정적 사이트만 지원 (SSR 불필요)
- Vite가 Next.js보다 빌드 빠름 (개발 속도)
- 라우팅이 단순함 (Landing → LevelSelect → Level)
- 번들 크기 작음 (모바일 최적화)

**트레이드오프**:
- SEO 불필요 (검색 대상 아님, 직접 링크 공유)
- SSR 없음 (초기 로딩은 CSR, 하지만 정적 파일이라 충분히 빠름)

---

### ADR-002: TypeScript strict mode
**결정**: TypeScript 5.0+, strict: true
**이유**:
- 블록 타입, 레벨 설정 등 복잡한 데이터 구조 → 타입 안정성 필수
- 런타임 에러 사전 방지 (학생 실습 중 크래시 방지)
- IDE 자동완성으로 개발 속도 향상

**트레이드오프**:
- 초기 타입 정의 시간 소요 (하지만 장기적으로 이득)
- 학습 곡선 (팀원이 TS 익숙해야 함)

---

### ADR-003: Zustand (Redux 대신)
**결정**: Zustand로 상태 관리
**이유**:
- 보일러플레이트 최소 (Redux Toolkit보다도 간단)
- 번들 크기 작음 (~1KB)
- localStorage 연동 간단 (persist middleware)
- 학습 곡선 낮음

**트레이드오프**:
- DevTools 지원 약함 (하지만 단순한 상태라 디버깅 쉬움)
- 대규모 앱에는 부족 (하지만 우리는 작은 앱)

---

### ADR-004: Canvas + Framer Motion 하이브리드
**결정**: 정적 요소는 Canvas/CSS, 애니메이션은 Framer Motion
**이유**:
- Canvas: 격자, 배경, 이동 경로 (정적/간단한 도형)
- Framer Motion: 인덕이 이동, UI 애니메이션 (부드러운 애니메이션)
- 각 기술의 장점 활용

**구체적 사용**:
- 격자/배경: Canvas API 또는 CSS Grid
- 인덕이: `<motion.div>` (translate, scale, rotate)
- 이동 경로: Canvas `drawLine()` 또는 SVG `<path>`
- UI: Framer Motion (모달, 버튼, 별 획득)

**트레이드오프**:
- 두 기술 혼용 → 약간의 복잡도 증가
- 하지만 성능과 개발 속도 모두 확보

**대안**: React Konva는 오버스펙. 순수 Canvas는 애니메이션 복잡.

### ADR-005: GitHub Pages (서버 없음)
**결정**: GitHub Pages 정적 호스팅, 서버 없음
**이유**:
- 무료, 안정적, HTTPS 자동
- 동시 접속 100명도 문제없음 (CDN)
- 유지보수 불필요 (NAS 서버 대비)
- git push만 하면 자동 배포 (GitHub Actions)

**트레이드오프**:
- 백엔드 기능 없음 (하지만 필요 없음)
- 사용자 데이터 수집 불가 (하지만 localStorage로 충분)
- 작품 공유는 URL 파라미터로 해결

---

### ADR-006: localStorage (DB 없음)
**결정**: localStorage로 진행 상황 저장
**이유**:
- 10분 실습이라 영구 저장 불필요
- 같은 브라우저에서 이어하기 가능
- 서버 불필요
- 즉시 저장/로드 (지연 없음)

**트레이드오프**:
- 브라우저 바꾸면 데이터 사라짐 (하지만 10분이라 재도전 가능)
- 용량 제한 (~5MB, 하지만 충분)
- 기기 간 동기화 불가 (하지만 모바일만 사용)

---

### ADR-007: Tailwind CSS (Styled Components 대신)
**결정**: Tailwind CSS로 스타일링
**이유**:
- 유틸리티 클래스로 빠른 개발
- 번들 크기 작음 (PurgeCSS)
- 반응형 간단 (`md:`, `lg:`)
- 모바일 우선 (`sm:` 없으면 모바일 기본)

**트레이드오프**:
- 클래스명 길어짐 (하지만 가독성은 괜찮음)
- 커스텀 디자인 어려움 (하지만 우리는 단순한 디자인)

---

### ADR-008: Framer Motion (애니메이션)
**결정**: Framer Motion으로 애니메이션
**이유**:
- 선언적 애니메이션 (코드 간결)
- React와 찰떡궁합
- 스프링 애니메이션 내장
- 터치 제스처 지원

**트레이드오프**:
- 번들 크기 증가 (~50KB, 하지만 필수 기능)
- CSS transition보다 무거움 (하지만 성능 충분)

---

### ADR-009: 상하좌우 이동 (회전 대신)
**결정**: 절대 방향 (⬆️⬇️⬅️➡️) 사용, 회전/각도 없음
**이유**:
- 직관적 (화면 기준 방향)
- 수학 불필요 (120도 같은 계산 없음)
- 모바일에서 이해 쉬움
- 10분 안에 학습 가능

**트레이드오프**:
- 터틀 그래픽 정통성 낮음 (하지만 교육 효과는 동일)
- 원/별 그리기 어려움 (하지만 사각형/계단만으로 충분)

### ADR-010: 블록 타입 최소화
**결정**: MVP는 이동 4개 + 반복 1개 + 스타일 3개 = 총 8개 블록
**이유**:
- 10분에 배우기 적절한 양
- 조건문(if) 제외 → 복잡도 감소
- 반복에만 집중 → 핵심 개념 강조

**트레이드오프**:
- 확장성 제한 (하지만 Phase 2에서 추가 가능)
- 복잡한 로직 불가 (하지만 교육 목적엔 충분)

**제외한 블록**:
- `if (조건)`: 시간 부족, 개념 어려움
- `변수`: 오버스펙
- `함수 정의`: 오버스펙
- `회전 (각도)`: 수학적 부담

---

### ADR-011: 인덕이 캐릭터 (PNG 이미지)
**결정**: 인덕이를 PNG 이미지로 제공 (SVG/애니메이션 없음)
**이유**:
- 빠른 구현 (기존 이미지 활용)
- 로딩 빠름 (작은 파일 크기)
- 브랜드 일관성 (인하대 공식 마스코트)

**트레이드오프**:
- 해상도 제한 (하지만 모바일 화면에 충분)
- 애니메이션 제한 (하지만 CSS transform으로 이동/회전)

**Phase 2 고려사항**: SVG로 변환 시 표정 변화 추가 가능

### ADR-012: 스테이지 2 "귀찮음 전략"
**결정**: 스테이지 2에서 먼저 수동 10개 블록 추가 → 이후 반복 블록 제공
**이유**:
- 체험 중심 학습 (설명보다 경험)
- 반복문 필요성을 몸소 체감
- 프로그래밍의 본질(귀찮은 일 줄이기) 이해
- 비교 화면으로 효과 극대화 (10줄 → 2줄)

**트레이드오프**:
- 처음엔 귀찮아할 수 있음 (하지만 그게 의도)
- 이탈 가능성 (하지만 30초면 끝남)

**검증**: 실제 학생 테스트에서 반응 확인 필요

### ADR-013: 힌트 시스템 (30초 후)
**결정**: 30초 경과 시 힌트 제공, 선택적 사용
**이유**:
- 막힘 방지 (이탈 감소)
- 자기 주도 학습 (선택권)
- 별점 차등 (힌트 사용 시 별 감소)

**트레이드오프**:
- 힌트 의존도 증가 가능 (하지만 별 인센티브로 완화)
- 힌트 작성 비용 (레벨당 2-3개)

### ADR-015: Phase 분할
**결정**: 3개 Phase로 개발 분할
**Phase 1 (MVP)**: 6개 핵심 스테이지 + 온보딩 + 개선된 피드백
**Phase 2 (완성)**: Firebase 교사 모드 + PWA + 뱃지
**Phase 3 (다듬기)**: 사운드 + 보너스 스테이지 + 최적화

**이유**:
- 빠른 검증 (Phase 1만으로 실습 가능)
- 점진적 개선
- 위험 분산 (Phase 1 실패 시 방향 전환 가능)

**트레이드오프**:
- 초기 기능 제한 (하지만 핵심은 있음)

### ADR-016: 스테이지 6개로 압축 (Phase 1 개선)
**결정**: 8개 스테이지 → 6개 핵심 스테이지 + 보너스
**이유**:
- 10분에 8개는 빡빡함 (각 1.25분씩)
- 6개면 여유 있음 (약 8분, 2분 버퍼)
- 핵심 개념(반복)에 집중
- 완주율 증가 예상 (60-70% → 80-85%)

**트레이드오프**:
- 초기 콘텐츠 양 감소 (하지만 Phase 2에서 보너스 추가)
- 지그재그, 격자 패턴 제외 (하지만 교육 효과는 유지)

**핵심 스테이지**:
- 0: 튜토리얼
- 1: 계단 (방향 조합)
- 2: 반복의 발견 (핵심!)
- 3: 사각형 (반복 활용)
- 4: 미로 (문제 해결)
- 5: 자유 창작

### ADR-017: 스테이지 2 개선 - 능동적 발견 (Phase 1 개선)
**결정**: 블록 10개 → 5개, 힌트 발견 방식
**이유**:
- 10개는 너무 지루함 → 이탈 위험
- 5개면 부담 감소
- "힌트 보기" vs "계속하기" 선택권 → 능동성 증가
- 학생이 스스로 발견하는 경험 제공

**구현**:
```
블록 5개 추가 완료 시:
"💡 발견! 같은 블록을 계속 쓰고 있네요...
 더 쉬운 방법이 있을까요?"

[힌트 보기] → 반복 블록 소개
[계속하기] → 스스로 발견 기회
```

**트레이드오프**:
- 기존 "10개 → 2개" 비교보다 임팩트 약함 (60% vs 80% 감소)
- 하지만 이탈률 감소가 더 중요

**검증 필요**:
- 실제 학생 테스트로 "힌트 보기" 선택률 확인
- 이탈률 비교 (기존 방식 vs 개선 방식)

### ADR-018: 실행 속도 조절 (Phase 1 추가)
**결정**: 보통/빠르게/건너뛰기 3단계 속도 제공
**이유**:
- 블록 많을 때 0.3초/칸은 오래 걸림 (지루함)
- 빠른 학생은 빠르게, 느린 학생은 천천히
- 디버깅 시 건너뛰기 유용

**구현**:
```
[▶️ 보통] 0.3초/칸 (기본)
[⏩ 빠르게] 0.1초/칸
[⏭️ 건너뛰기] 즉시 결과
```

**트레이드오프**:
- UI 복잡도 증가 (버튼 3개)
- 하지만 UX 개선 효과 큼

---

### ADR-019: 에러 피드백 개선 (Phase 1 추가)
**결정**: "벽에 부딪혔어요" → "3번째 블록에서 벽에 부딪혔어요"
**이유**:
- 어디서 틀렸는지 모르면 수정 어려움
- 구체적 위치 + 시각적 강조 → 빠른 수정
- 학습 효과 증가

**구현**:
```
내 코드:
1. ➡️ 오른쪽  ✅
2. ➡️ 오른쪽  ✅
3. ➡️ 오른쪽  ❌ ← 여기서 멈췄어요!
4. ⬆️ 위로

[3번 블록 삭제] [다시 실행]
```

**트레이드오프**:
- 구현 복잡도 증가 (에러 발생 지점 추적 필요)
- 하지만 학생 경험 개선 효과 큼

### ADR-020: 교사 모드 Phase 2로 이동 (Firebase)
**결정**: Phase 1은 완전히 서버 없음, Phase 2에서 Firebase 추가
**이유**:
- ADR-005 "서버 없음" 원칙 준수
- 10분 실습에는 교사 대시보드 과한 기능
- 선생님이 돌아다니며 확인하는 게 더 교육적
- Phase 1 완료 후 필요성 검증

**Phase 1 대안**:
- 학생 화면 상단에 진행 상황 크게 표시
  ```
  📍 3/6 단계  ⭐⭐⭐ 9개
  ```
- 선생님이 멀리서도 확인 가능
- 개별 지도 용이

**Phase 2 (필요 시)**:
- Firebase Realtime Database (무료 티어)
- room 코드로 반 구분
- 익명 접속 (개인정보 불필요)
- 실시간 진행도 대시보드

**트레이드오프**:
- Phase 1에서 실시간 모니터링 불가
- 하지만 원칙 준수 + MVP 단순화
